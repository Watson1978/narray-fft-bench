# narray-fft-bench

`Cumo::FFT`（cuFFT 実装）を、numo-pocketfft との互換（計算結果を含む）と、CuPy に対する速さの 2 点で確かめるベンチマーク。7 つの題材（Whisper のメル特徴量、2D スペクトル法、3D Poisson、多倍長整数の乗算、位相相関、OFDM、スペクトル推定）を、Numo / Cumo / numpy+scipy / CuPy の 4 実装で、同じ fixture から同じアルゴリズムで動かす。

計画は [docs/plans/narray-fft-bench-plan.md](docs/plans/narray-fft-bench-plan.md)、作法は [AGENTS.md](AGENTS.md)、測り方は [docs/method.md](docs/method.md)、CuPy との挙動の差は [docs/cupy-notes.md](docs/cupy-notes.md)。

## 結論

2026-10-17〜22。B、C、E は 2026-10-22 に cumo 0.14.1 で測り直した。A と F は 0.14.0、D と G は master `e9ae5d76` で測ったまま。A、D、F、G のステップは 0.14.1 の変更（#632）を使わないので、各 1 条件を同じラウンドで交互に測って、0.14.0 と変わらないことを確かめた（[cumo-0.14.1](docs/results/cumo-0.14.1.md)）。2026-11-03 に、cumo 0.15.0 でも 7 題材の定常が 0.14.1 と変わらないことを、同じラウンドで交互に測って確かめた（[cumo-0.15.0](docs/results/cumo-0.15.0.md)）。関門の値はどのビルドでもビットまで同じ。環境は CuPy 14.2.0、numpy 2.5.3、scipy 1.18.1、numo-pocketfft 0.7.0、RTX 5070 Ti Laptop（12 GB）で、SM とメモリのクロックを固定した。

- **正しさの関門は 7 題材とも、4 実装と fp64 / fp32 のすべてで通る。** A・D・E・F の完全一致の関門（桁、シフト量、ビット）も含む。`Cumo::Pocketfft` は numo-pocketfft と 887 ケースで、返る型、形、例外、値が一致した（0 次元の入力だけは、cumo が意図して `DimensionError` を投げる。[pocketfft-compat](docs/results/pocketfft-compat.md)）。
- **小さい変換や、呼び出しの多いステップでは、Cumo が CuPy より速い**（1.1〜2.2 倍）。1 本ずつ 10000 回の OFDM で 1.71 倍、Welch 法で 1.55〜1.63 倍、プランキャッシュを溢れさせる条件で 1.55 倍。Cumo がカーネル 1 本を起動する手間は、CuPy の半分ほど。
- **大きい配列では、Cumo が CuPy より遅いことが多い**（CuPy ÷ Cumo で 0.51〜0.98）。主な原因は Ruby の GC。cumo は GPU のメモリの確保を Ruby に知らせるので、数 MB 以上の一時配列を作ると minor GC が頻繁に走る（16 MB を超える配列では、作るたびに走ると見ている）。2D スペクトル法（fp32、2048²）では、1 ステップ 11.8 ms のうち 11.0 ms が GC だった（0.14.1、単発。[B](docs/results/taylor_green.md)）。OFDM（64 × 10000 本）では一時配列をすぐ解放すると CuPy と並んだ（[F](docs/results/ofdm.md)）。
- **cumo 0.14.1 で、複素数と実数を混ぜた演算が、実数を複素数に変換しなくなった（#632）。** 同じラウンドで交互に測ると、0.14.0 より E が 1.03〜1.07 倍、B が 1.10〜1.18 倍、C が 1.10〜1.12 倍速くなった。B は一時配列が減って GC が減り、3D Poisson の `rfftn` は CuPy と並んだ（[cumo-0.14.1](docs/results/cumo-0.14.1.md)）。
- **3 軸のうち 2 軸だけの変換（512³）では、Cumo が CuPy の 6.4 倍速い。** CuPy は配列をストライドのまま cuFFT に渡し（advanced layout）、このときの cuFFT のカーネルが遅い。Cumo は転置してから連続した配列を変換する（[C](docs/results/poisson3d.md)）。
- **プロセスの最初の呼び出しは、Cumo が CuPy の 1.6〜14 倍遅い。** D で切り分けると、遅い原因は cuFFT のプランの生成ではなく、cumo の要素ごとの演算のカーネルを最初に読み込む手間だった（[D](docs/results/bignum_mul.md)）。cumo 0.15.0 では、ステップが縮約を使う A、E、G の初回が、0.14.1 より 1.15〜1.60 倍速くなった。縮約のカーネルを分けた #634 の効果と見ている。
- CPU では、numpy+scipy が Numo（numo-pocketfft）より速いことが多い（多くの条件で 1.2〜17 倍）。1 次元の長い `rfft` / `irfft`（G の自己相関と D の手書きの経路）では、Numo が 1.1〜1.35 倍速い。

## 読み方

- 数字は `bench/run.sh` で 10 ラウンド測った中央値で、単位は ms / ステップ。1 ラウンドの中で、Cumo、CuPy、対照の Cumo を、順番を回しながら交互に動かす。定常はウォームアップ 1 区間のあとの best-of-3。
- **比は CuPy ÷ Cumo で、1 を超えれば Cumo が速い。** 後ろの n/10 は、10 ラウンドのうち比が 1 を超えたラウンドの数。「またぐ」は、比に 1 より大きいラウンドと小さいラウンドの両方があったもので、差があるとは読まない。
- 対照（Cumo ÷ Cumo）が 1 をまたがなかった条件は載せない（D の fp64 の 10⁴、A の CPU の初回）。E の `rfft2` の 1024² は、10/18 の回では対照が 1 をまたがなかったが、10/22 の測り直しではまたいだので載せた。
- 各ステップの中身、全条件の表、原因の内訳は、題材ごとの結果のページにある。

## CPU（Numo / numpy+scipy、fp64）

比は numpy ÷ Numo で、1 を超えれば Numo が速い。各題材の代表の条件だけを載せる。全部の表は各題材のページにある。

| 題材と条件 | Numo | numpy | numpy ÷ Numo |
|---|---|---|---|
| A、`rfft`、3000 フレーム | 18.2 | 8.30 | 0.451 0/10 |
| B、N = 1024 | 260 | 158 | 0.608 0/10 |
| C、`rfftn`、256³ | 1193 | 257 | 0.215 0/10 |
| D、`fftconvolve`、10⁶ 桁 | 859 | 49.9 | 0.058 0/10 |

| F、64 × 10000 本 | 15.1 | 4.87 | 0.323 0/10 |

| G、Welch、L = 1024、長さ 75600 | 1.26 | 0.334 | 0.265 0/10 |

D の `fftconvolve` で Numo が 17 倍遅いのは呼び出し方の差で、numo-pocketfft は長さを伸ばさずに複素数の変換を 3 回かけ、scipy は速い長さに伸ばして実数の変換で済ませる。A の DFT の行列積は BLAS の複数のスレッドで動き、FFT は 1 スレッド。

## 動かし方

```
bundle install
python3 -m venv python/.venv
python/.venv/bin/pip install -r python/requirements.txt
rake fixtures
rake test
```

GPU を使うときは、[AGENTS.md](AGENTS.md) の「cumo の版」の手順で `vendor/` に cumo 0.15.0 を入れる。計測するときは、`rake fixtures:all` のあとで `bench/run.sh bench/conditions.tsv tmp/bench`（GPU）と `bench/run.sh bench/conditions_cpu.tsv tmp/bench_cpu`（CPU）を実行する。GPU の計測の前に、SM とメモリのクロックを固定する。
