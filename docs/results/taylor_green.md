# B. 2 次元のスペクトル法（Taylor–Green 渦）

周期境界の [0, 2π)² で、2 次元の非圧縮 Navier–Stokes 方程式を渦度の形 ∂ω/∂t + ∇·(uω) = ν∇²ω で解く。空間は擬スペクトル法（`rfft2` / `irfft2`）、時間は積分因子つきの RK4。2026-10-18、cumo 0.14.0（`vendor/cumo-0.14.0/`。GPU の表は 2026-10-22 に cumo 0.14.1 で測り直した）、CuPy 14.2.0、numpy 2.5.3、numo-pocketfft 0.7.0、RTX 5070 Ti Laptop（12 GB）。

## 手順

- 波数は `fftfreq(N, d: 1/N)`（第 0 軸）と `rfftfreq(N, d: 1/N)`（第 1 軸、片側）。流れ関数は ψ̂ = ω̂ / k²（k = 0 は 0）、速度は u = ∂ψ/∂y、v = −∂ψ/∂x。
- **非線形項は、保存形 ∇·(uω) = ∂(uω)/∂x + ∂(vω)/∂y で作る。** 右辺の 1 回の評価は、`irfft2` 3 回（u、v、ω）と `rfft2` 2 回（uω、vω）。RK4 は 1 ステップに右辺を 4 回評価するので、1 ステップは `irfft2` 12 回と `rfft2` 8 回になる。計画は「1 ステップに `rfft2` 3 回 + `irfft2` 3 回」としていたが、RK4 の 4 段を数えるとこうなる。
- **dealias は 2/3 則で、|k_x| < N/3 かつ |k_y| < N/3 の成分だけを残す**（非線形項のスペクトルに掛ける）。ω̂ がこの範囲の内側にあれば、積 uω の成分は各軸で 2N/3 未満なので、折り返しはすべて N/3 以上に落ち、マスクで消える。乱数の初期場は fixture で |k| ≤ N/3 に切ってあるので、この範囲の内側にある。
- 時間積分は、粘性の項を E = exp(−νk²dt) で厳密に扱う RK4（Trefethen の『Spectral Methods in MATLAB』の形）。
- マスクは Ruby の配列（Python のリスト）から作り、Bit 配列を使わない。
- 時間発展のループの中では読み戻さない。エネルギーなどの和は、デバイスの 0 次元の配列のまま持ち、ループのあとで読む。

## 関門

| 関門 | 中身 | tol（fp64 / fp32） |
|---|---|---|
| `taylor.error` | Taylor–Green（ω₀ = 2 sin x sin y、ν = 0.05、dt = 0.01、100 ステップで t = 1）と、解析解 ω₀ e^{−2νt} の相対差 | 1e-8（計画のまま） / 5.2e-5 |
| `random.energy_drift` | 乱数の初期場（ν = 0）を 100 ステップ進めたときの、エネルギー Σ(\|û\|² + \|v̂\|²) の相対変化 | 1e-6（計画のまま） / 3.3e-6 |
| `random.enstrophy_drift` | 同じく、エンストロフィー Σ\|ω̂\|² の相対変化 | 1e-6 / 3.3e-6 |
| `random.parseval` | 各ステップ（0〜100）の、Σω² · N² と Σ\|ω̂\|² の相対差の最大 | 4.9e-14 / 6e-6 |
| `round_trip` | `irfft2(rfft2(ω), s: [N, N])` と ω | 4.9e-14 / 6e-6 |
| `transposed` | `rfft2(ω.transpose, axes: [-1, -2]).transpose` と `rfft2(ω)`（`axes:` の明示） | 4.9e-14 / 6e-6 |
| `fftshift` | `fftshift(fftfreq(N, d: 1/N))` が −N/2 から昇順に並ぶ（違う要素の数が 0） | 0 |

スペクトルの和は、`rfft2` が残す片側から、第 1 列と Nyquist の列を除いて 2 倍に数える。fp64 の tol は、計画に数字があるものはそのまま使い、無いものは Numo で測った最大（Parseval の 4.885e-15）の 10 倍にした。fp32 は、numpy、CuPy、Cumo の最大の 10 倍。

- 4 実装とも、fp64 と fp32 で 7 個の関門がすべて通る。`values`（Taylor–Green の t = 1 のピーク 1.8097、乱数の初期場のエネルギーとエンストロフィーの最初と最後）は、fp64 の 4 実装で 1e-9 の内側、fp32 の 3 実装で 1e-3 の内側に揃う（`script/compare_gates.rb`）。
- **Taylor–Green の誤差は 3e-15 で、計画の 1e-8 よりずっと小さい。** 非線形項が丸めの範囲で 0 になり、粘性の減衰は積分因子で厳密に扱うため。
- **fp64 のエネルギーとエンストロフィーのずれ（1.3e-10 と 3.0e-8）は、4 実装で同じ値になる。** 2/3 則の打ち切りは、エネルギーとエンストロフィーを空間の離散化では厳密に保存するので、残るのは RK4 の時間の打ち切りの誤差。丸めでは決まらないので、実装によらない。
- fp32 の Cumo のエンストロフィーのずれが 0 になったのは、最初と最後の値が単精度でたまたま同じになったため。
- Numo シムと `Cumo::FFT` の直接比較（`test/test_parity.rb` の B の呼び出し 7 種）の差は、最大 5.70e-16（`irfft2`）。

## 速さ

1 ステップは、乱数の初期場（ν = 0.05、dt = 0.01）から積分因子つきの RK4 を 1 回進める（`irfft2` 12 回、`rfft2` 8 回と、要素ごとの演算）。毎回同じ ω̂ から進め、状態は持ち越さない。大きい N では dt = 0.01 が CFL 条件を超え、何千ステップも続けると発散するため。比は numpy ÷ Numo（CuPy ÷ Cumo）で、1 を超えれば Ruby 側が速い。後ろの n/10 は、10 ラウンドのうち比が 1 を超えたラウンドの数。

- **小さい N では Cumo が速い（N = 64 で 2.1 倍）。** 1 ステップに 20 回の変換と、その何倍もの要素ごとの演算を呼ぶので、呼び出しの手間で決まる区間では、F の `single` や G の Welch と同じく Cumo の手間の小ささが出る。
- **fp64 の N = 512〜2048 では、CuPy が 2〜5% 速い。** N = 4096 では差が無い（比が 1 をまたぐ）。GPU の時間で決まる区間で、E の fp64 と同じ向き（E では 14〜23%）。
- **fp32 の N = 1024〜4096 では、Cumo が 1.1〜1.9 倍遅い。原因は Ruby の GC だった**（下）。
- **0.14.1 で、どの条件も Cumo の側に動いた。** fp32 の N = 2048 は 0.441 から 0.522 に、N = 64 は 1.890 から 2.078 になった。大きい N では、複素数の一時配列が減って GC が減り、小さい N では、カーネルの起動が減った分と見ている。
- 初回は Cumo が CuPy の 3.5 倍遅い。D と同じく、要素ごとの演算のカーネルの読み込みが入っていると見ている（B では確かめていない）。
- 計画の見どころは「1 ステップに同じ形の変換が続くのでプランキャッシュが完全に効く。ここで CuPy に負けるなら、ラッパーの前後処理（C2R の退避コピー、正規化）が原因」としていた。fp32 の大きい N で負けた原因は、前後処理ではなく GC だった。

#### fp32 で Cumo が遅い理由

同じステップを繰り返して `GC.stat` を数えると、GC の時間が 1 ステップの時間のほとんどを占めていた（単発、cumo 0.14.0）。

| N（fp32） | ms/ステップ | 1 ステップあたりの GC | GC の時間（1 ステップあたり） |
|---|---|---|---|
| 512 | 0.647 | minor 2.9 回 | 0.3 ms |
| 1024 | 1.65 | minor 11 回、major 0.2 回 | 1.2 ms |
| 2048 | 12.8 | minor 41 回、major 5 回 | 12.0 ms |
| 4096 | 44.3 | minor 72 回、major 22 回 | 42.7 ms |

0.14.1 では、複素数と実数を混ぜた演算の一時配列が無くなり、N = 2048 の GC は minor 38.5 回、major 4 回、11.0 ms / ステップに減った（同じ日に同じ数え方で、0.14.0 は minor 41 回、major 5 回、13.1 ms。[cumo-0.14.1.md](cumo-0.14.1.md)）。それでも、1 ステップの時間のほとんどが GC であることは変わらない。

cumo は GPU のメモリの確保を `rb_gc_adjust_memory_usage` で Ruby に知らせる（F の「batch で Cumo が遅い理由」）。N = 2048 の片側スペクトル（2048 × 1025 の SComplex）は 1 本 16.8 MB で、Ruby の malloc の上限（既定で 16 MB）を 1 本で超えるので、配列を作るたびに GC が起きる、と見ている。fp64 でも同じように GC は起きるが、GPU の時間がずっと長い（N = 2048 で 38 ms と、fp32 の 6.3 ms の 6 倍）ので、GC のホストの時間がその陰に隠れ、差が 6〜7%（0.14.1 では 2〜5%）にとどまると見ている。

Ruby の GC の上限を上げると、GC の時間はほぼ 0 になり、CuPy の 1.07〜1.12 倍まで戻った（単発）。

| 設定 | N = 1024 | N = 2048 |
|---|---|---|
| 既定 | 1.64 ms | 12.7 ms |
| `RUBY_GC_MALLOC_LIMIT=268435456`、`RUBY_GC_MALLOC_LIMIT_MAX=1073741824` | 1.31 ms | 6.97 ms |
| 上に加えて `RUBY_GC_OLDMALLOC_LIMIT=1073741824`、`RUBY_GC_OLDMALLOC_LIMIT_MAX=4294967296` | 1.28 ms | 7.07 ms |
| CuPy（計測の表） | 1.20 ms | 6.29 ms |

ただし、上限を上げるとメモリプールが大きくなる（N = 2048 で 495 MB から 2485 MB、N = 1024 で 210 MB から 2351 MB）。cumo が確保を Ruby に知らせるのは、GC が GPU のメモリを知らずにプールが際限なく増えるのを防ぐため（cumo #221）なので、上限を上げるだけでは解決にならない（cumo 側のセッションの指摘）。F（64 × 10000 本、1 本 5.8 MB）では、同じ設定で 1 ステップがかえって遅くなった。配列が小さいと GC 1 回の時間が短く、GC が減って一時配列のメモリが使い回されなくなる損のほうが大きいためと見ている。計測の表は、どの題材も既定の GC の設定で取っている。
