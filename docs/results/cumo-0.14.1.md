# cumo 0.14.1

2026-10-22、cumo 0.14.1（タグ `v0.14.1`、master `58f5ee20`）を `vendor/cumo-0.14.1/` に入れ、既定をこれに替えた。0.14.0 からの変更のうち、このリポジトリの題材に効くのは #632 だけ。#632 では、同じ精度の複素数と実数の + − × ÷ が、実数を複素数の一時配列に変換せずに計算するようになった。直ったのは同じ精度の組だけで、Ruby の Complex のスカラー、精度の違う組（DComplex と SFloat など）、整数と複素数は、0.14.1 でも変換する。`Cumo::FFT` と `Cumo::Pocketfft` は変わっていない（どちらも cumo 側のセッションからの連絡）。ほかの変更は、ホストループの読み直しの修正（#630、#631）と、`Cumo::REVISION` が `"v0.14.1"` を返すようにした修正（#626）。

## 正しさ

- 7 題材の関門の値と `values` は、small の fp64 と fp32、E の n1024 で、0.14.0 とビットまで同じだった（`script/gate.rb` の JSON の `problems` を比べた）。D の fp32 の small は、両方の版で同じ値で外れる。基数 10⁴ では fp32 の桁が足りないためで、[bignum_mul.md](bignum_mul.md) に書いた既知の挙動。
- `GPU=1 rake test` は、0.14.1 で 65 件すべて通った。

## 変わったカーネル

nsys で、100 万要素の fp32 の演算を 10 回ずつ数えた。`c` は SComplex、`r` は SFloat。

| 演算 | 0.14.0 | 0.14.1 |
|---|---|---|
| `c * r` | `store_sfloat`（実数を SComplex に変換）と `mul` | `mul_r` |
| `r * c` | `store_sfloat` と `mul` | `mul_r` |
| `c / r` | `store_sfloat` と `div` | `div_r` |
| `c + r` | `store_sfloat` と `add` | `add_r` |

**0.14.0 では、4 つの演算とも、どちらの順序でも、変換のカーネルが 1 本多かった。** このリポジトリの文書には、cumo 側のセッションの当初の見立てに従って「割り算だけが変換し、`SComplex * SFloat` は変換しない」と書いていたが、誤りだった。cumo 側も 2026-10-20 に、`SComplex.cast` の呼び出しを数えて同じ訂正をしている。

変換は、一時配列も 1 本増やしていた。400 万要素（SComplex で 32 MB）で同じ演算を 200 回続けると、Ruby の GC は 0.14.0 で 200 回、0.14.1 で 100 回走った（`c * c` は両方の版で 100 回）。

## 0.14.0 との比べ

`bench/run.sh` の Ruby の列に 0.14.1、Python の列に 0.14.0 を置き（`CUMO_LIB` で版を指定）、同じラウンドの中で交互に 10 ラウンド測った。2026-10-22 21:52〜22:14 と 23:30〜23:38、クロックは固定のまま（始める前のアイドルの SM が 2797 MHz）。cumo 側のセッションは GPU を使っていなかった。比は 0.14.0 ÷ 0.14.1 で、1 を超えれば 0.14.1 が速い。対照 ÷ 0.14.1 は、すべての条件で 1 をまたいだ。幅が 5% を超えた系列は生の値をラウンド順に見て、2 つの群には分かれていなかった。

| 定常 | 0.14.1 (ms) | 0.14.0 (ms) | 0.14.0 ÷ 0.14.1 |
|---|---|---|---|
| E、`fft2`、1024²、fp32 | 0.290 | 0.295 | 1.010 7/10（またぐ） |
| E、`fft2`、2048²、fp32 | 2.46 | 2.43 | 0.982 2/10（またぐ） |
| E、`fft2`、4096²、fp32 | 8.82 | 9.41 | 1.066 10/10 |
| E、`fft2`、2048²、fp64 | 9.33 | 9.87 | 1.058 10/10 |
| E、`rfft2`、1024²、fp32 | 0.154 | 0.157 | 1.032 10/10 |
| E、`rfft2`、2048²、fp32 | 0.603 | 0.638 | 1.050 10/10 |
| E、`rfft2`、4096²、fp32 | 4.39 | 4.56 | 1.033 10/10 |
| B、N = 1024、fp32 | 1.77 | 1.94 | 1.098 10/10 |
| B、N = 2048、fp32 | 11.9 | 14.1 | 1.184 10/10 |
| C、`rfftn`、256³、fp32 | 2.25 | 2.53 | 1.124 10/10 |
| C、`fftn`、256³、fp32 | 4.92 | 5.45 | 1.105 10/10 |
| A、`rfft`、3000 フレーム、fp32 | 0.227 | 0.224 | 0.986 4/10（またぐ） |
| D、`fftconvolve`、10⁵ 桁、fp32 | 0.082 | 0.082 | 1.004 5/10（またぐ） |
| F、64 × 10000 本、fp32 | 0.099 | 0.101 | 1.014 6/10（またぐ） |
| G、Welch、L = 1024、fp32 | 0.096 | 0.096 | 0.993 4/10（またぐ） |

| 初回 | 0.14.1 (ms) | 0.14.0 (ms) | 0.14.0 ÷ 0.14.1 |
|---|---|---|---|
| E、`fft2`、1024²、fp32 | 55.7 | 53.5 | 0.972 2/10（またぐ） |

- **E、B、C が速くなり、A、D、F、G は変わらなかった。** E は `cross / cross.abs` で、B は 1/k²、マスク、積分因子を掛けるたびに、C は 1/k² を掛けるときに、複素数と実数を混ぜる。A、D、F、G のステップは、複素数と実数の配列を混ぜた演算を使わない。
- **E の n = 1024 の `fft2` は変わらなかった**（cumo 側の見込みどおり）。`rfft2` は 1024² でも 3% 速くなった。`fft2` の 1 ステップのカーネルを nsys で数えると（`--inner` 1000 と 3000 の差）、次のようになった。
  - `cross / cross.abs` は、0.14.0 では `store_sfloat` 20.5 µs と `div_vec` 17.0 µs の 2 本だった。0.14.1 では `div_r` 1 本の 21.6 µs になり、16 µs 減った。
  - 同じステップの `div_vec`（`ifft2` の正規化。100 万要素の複素数どうし）は 16.9 µs。`div_r` は読む量が 4 MB 少ないのに、それより 4.7 µs 遅い。`div_r` のカーネルの名前は `cumo_iter_scomplex_div_r_kernel_dim1` で、`_vec` ではない。cumo 側のセッションがソースで確かめたところ、#632 で足した `_r` のカーネルは汎用の反復子の版しか持たず、連続した配列でも `_dim1` を通る。複素数どうしの演算には、1 スレッドが 16 バイトずつ動かす `_vec` の版がある。4.7 µs の差がこのためかは、まだ測っていない（疑い）。cumo 側のトラッカーに、フォローアップとして記録された。
  - カーネルの時間の合計は、293.8 µs から 282.5 µs に減った。1 ステップの時間（0.295 → 0.290 ms）とカーネルの合計との差は、1 µs から 8 µs に開いた。GPU の時間が減った分、ホストの側が見え始めたと見ている（確かめていない）。
  - FFT の入力を複素数にする `store_sfloat` の 2 本（`fft2(I)` と `fft2(J)` の中）は、両方の版にある。
- **E の 2048² の fp32 の `fft2` も変わらなかった。** cumo 側は 2048² から効くと見ていた。下の GC の数え方では、1 ステップ 2.4 ms のうち 2.3 ms が GC の時間で、GC の回数は両方の版で同じだった。ホストの GC が 1 ステップの時間を決めているので、カーネルが 1 本減っても見えないと見ている（確かめていない）。
- 初回は変わらなかった。

## GC

同じステップを繰り返し、`GC.stat` の差を回数で割った（単発、fp32、同じ日に 2 つの版で）。

| 条件（fp32） | 1 ステップ（ms） | GC の時間（ms / ステップ） | minor | major |
|---|---|---|---|---|
| B、N = 1024 | 1.97 → 1.77 | 1.50 → 1.36 | 11.3 → 10.4 | 0.20 → 0.18 |
| B、N = 2048 | 14.0 → 11.8 | 13.1 → 11.0 | 41.0 → 38.5 | 5.0 → 4.0 |
| B、N = 4096 | 46.3 → 42.3 | 44.3 → 39.5 | 71.5 → 67.0 | 21.5 → 19.0 |
| C、`rfftn`、256³ | 2.77 → 2.88 | 1.13 → 1.15 | 2.5 → 2.5 | 0.5 → 0.5 |
| C、`rfftn`、512³ | 22.4 → 20.7 | 2.82 → 2.65 | 1.5 → 1.5 | 1.5 → 1.5 |
| C、`fftn`、256³ | 6.51 → 6.29 | 3.71 → 3.77 | 3.0 → 3.0 | 2.0 → 2.0 |
| E、`fft2`、2048² | 2.38 → 2.43 | 2.25 → 2.29 | 5.0 → 5.0 | 1.0 → 1.0 |
| E、`fft2`、4096² | 10.8 → 9.53 | 7.72 → 6.81 | 7.0 → 7.5 | 4.0 → 3.5 |

- **B の N = 2048 では、GC の時間が 2.1 ms 減った。** 計測の表の差（14.1 → 11.9 ms）と同じ大きさ。変換の一時配列が無くなり、GC の回数が減ったため。
- **C では、GC の回数が変わらなかった。** C の差は、変換のカーネルと、その一時配列に初めて書き込む手間の分と見ている（確かめていない）。256³ の `rfftn` で、単発の 1 ステップが計測の表と逆向きになったのは、単発のばらつきの範囲と見ている。表は 10 ラウンドの交互の計測から取る。

## CuPy との比

E、B、C の全条件を、0.14.1 と CuPy で測り直した（2026-10-22 22:17〜23:28、`bench/run.sh` の 10 ラウンド、対照系列付き）。表は題材ごとのページにある（[phase_correlation.md](phase_correlation.md)、[taylor_green.md](taylor_green.md)、[poisson3d.md](poisson3d.md)）。A と F の表は 0.14.0、D と G の表は master `e9ae5d76` で測ったまま。

## 再現

```
CUMO_NVCC_GENERATE_CODE=arch=compute_120,code=sm_120 gem install cumo -v 0.14.1 --no-document --ignore-dependencies --install-dir vendor/cumo-0.14.1
GPU=1 DTYPE=fp32 CUMO_LIB=$PWD/vendor/cumo-0.14.0/gems/cumo-0.14.0/lib ruby script/gate.rb --out tmp/gates/cumo-0.14.0.json
GPU=1 DTYPE=fp32 ruby script/gate.rb --out tmp/gates/cumo-0.14.1.json
```

交互の計測は、`bench/conditions.tsv` の行の Ruby のコマンドを 2 つの版の `CUMO_LIB` 付きに書き換え、Ruby と Python の列に置いて `bench/run.sh` に渡す（`bench/aggregate.py --labels 0.14.1,0.14.0`）。
