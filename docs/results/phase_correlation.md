# E. 位相相関による画像の位置合わせ

画像 I と、それをずらした J の位置合わせを、位相相関で行う。`F = fft2(I)`、`G = fft2(J)`、`R = F·conj(G) / |F·conj(G)|`、`r = fftshift(ifft2(R).real)` とし、r の最大の位置からずれを読む。2026-10-18、cumo master `e9ae5d76`（`vendor/cumo-e9ae5d76/`。GPU の表は 2026-10-22 に cumo 0.14.1 で測り直した）、CuPy 14.2.0、numpy 2.5.3、numo-pocketfft 0.7.0、RTX 5070 Ti Laptop（12 GB）。

## 入力

- 画像は、白色雑音に低域通過 1 / (1 + (k / k₀)²)（k₀ = n / 16）を掛け、RMS を 1 にしたもの（`script/make_fixtures.rb` の `texture`）。
- 整数シフトは、J = roll(I, s)（各軸 |s| < n / 4）。roll は題材のコードが、区間の外で行う（Ruby はスライスの代入 4 回、Python は `xp.roll`）。
- 小数シフトは、I の各ビンの位相を回して作った画像（fixture に入れてある）。
- small は n = 256 と奇数の 255 で、整数シフト 20 組、小数シフト 5 組。n1024 は 1024 と奇数の 1023 で、整数 4 組、小数 2 組。n512、n2048、n4096 は計測用で、奇数の画像は無い。

**テクスチャは、第一段階のガウス（exp(−k² / (2k₀²))）から、2026-10-18 にローレンツ型へ替えた。** ガウスでは、n = 256 のビンの 13% で、フィルタの値が 1e-16 を下回り、画像を倍精度に丸めた誤差より小さくなる。そこでは F·conj(G) の位相が丸めの雑音になり、整数シフトでもピークが 1 に届かなかった（Numo の small で 0.941〜0.966）。ローレンツ型では、フィルタの値の最小が 7.75e-3 で、どのビンも丸めより十分大きい。

## 経路

| 経路 | 呼び出し |
|---|---|
| `fft2` | `fftshift(ifft2(R).real)`、R は `fft2` 2 回から |
| `rfft2` | `fftshift(irfft2(R, s: [n, n]))`、R は `rfft2` 2 回から（片側スペクトル） |

## 関門

- `<画像>.wrong_shifts`: 2 経路とも、整数シフトを完全に当てる（違った数が 0）。`<画像>` は `even`（n）と `odd`（奇数の n）。
- `<画像>.paths_differ`: 整数シフトの r の、2 経路の差（相対、max ノルム）。fp64 で 2.2e-15、fp32 で 2.4e-6 以下。
- `<画像>.peak_min`: 整数シフトの r の最大値の、最小が 1 − tol 以上。tol は fp64 で 1e-10（計画のまま）、fp32 で 1.2e-6。
- `fractional.error`: 小数シフトの推定と真の値の差（各軸の最大）が 0.05 px 以下。
- `<画像>.shift_round_trip`: `fftshift(ifftshift(x))` と `ifftshift(fftshift(x))` が、x とビットまで一致する（違う要素の数が 0）。
- `values`: 整数シフトを当てた数、ピークの最小、小数シフトの推定値（組ごと、軸ごと）。

**小数シフトは、放物線ではなく、sinc の 3 点推定で読む**（2026-10-18、ユーザーの判断）。ピークを r₀、両隣のうち大きいほうを r₁ として、d = r₁ / (r₁ + r₀) とする（Foroosh、Zerubia、Berthod 2002）。位相相関のピークは sinc の形（正確には Dirichlet 核）をしているので、この式は n が大きければほぼ正確になる。計画は放物線フィットで 0.05 px 以内としていたが、放物線は sinc の形に合わず、Numo で次のようにずれた。

| サイズ | 放物線の誤差の最大 | sinc の 3 点推定の誤差の最大 |
|---|---|---|
| small（n = 256） | 0.120 px | 1.71e-3 px |
| n1024 | 0.098 px | 6.36e-4 px |
| n4096 | 0.119 px | 1.05e-4 px |

sinc の 3 点推定の誤差は、n が大きいほど小さくなる（n512 で 1.50e-3、n2048 で 2.21e-4）。n が偶数のときは、小数シフトの画像を作るときに Nyquist のビンの虚部を `.real` で落としているので、その分だけ正確な値からずれる。奇数の n = 255 で作った画像（scratchpad の試し）では、誤差は 2.4e-6 px だった。

tol は、Numo で測った値の 10 倍にした。fp32 は numo-pocketfft に単精度が無いので、numpy、CuPy、Cumo の最大の 10 倍にした。

## 関門の値

small（n = 256 と 255）。差とピークの不足は、偶数の画像 / 奇数の画像の順。

| | Numo | numpy | CuPy | Cumo |
|---|---|---|---|---|
| fp64 `wrong_shifts` | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |
| fp64 `paths_differ` | 1.53e-16 / 2.22e-16 | 1.11e-16 / 2.22e-16 | 2.10e-16 / 2.22e-16 | 1.99e-16 / 2.22e-16 |
| fp64 1 − `peak_min` | 0 / 2.22e-16 | 0 / 0 | 0 / 1.11e-16 | 0 / 2.22e-16 |
| fp64 `fractional.error` | 1.71e-3 | 1.71e-3 | 1.71e-3 | 1.71e-3 |
| fp32 `paths_differ` | | 1.19e-7 / 2.38e-7 | 8.94e-8 / 1.19e-7 | 1.19e-7 / 1.19e-7 |
| fp32 1 − `peak_min` | | 5.96e-8 / 0 | 1.19e-7 / 5.96e-8 | 1.19e-7 / 5.96e-8 |
| fp32 `fractional.error` | | 1.71e-3 | 1.71e-3 | 1.71e-3 |

- n1024（1024 と 1023）でも、4 実装と 2 つの dtype ですべて通る。fp64 の差は 1.25e-16 以下、ピークの不足は 2.22e-16 以下、小数シフトの誤差は 6.36e-4 px。fp32 のピークの不足は、CuPy と Cumo で 1.79e-7 だった。
- `shift_round_trip` は、すべての実装、dtype、サイズで 0。
- `values`（小数シフトの推定値 10 個、ピークの最小、当てた数）は、fp64 の 4 実装で 1e-9 の内側、fp32 の 3 実装で 1e-3 の内側に揃う（`script/compare_gates.rb`）。小数シフトの誤差が実装によらず 3 桁まで同じなのは、誤差の大半が推定の式と Nyquist のビンから来ていて、FFT の丸めからではないため。
- Numo シムと `Cumo::FFT` の直接比較（`test/test_parity.rb` の E の呼び出し 14 種）の差は、最大 5.59e-16（`irfft2`、n = 255）。fftshift と ifftshift は差 0。

## 速さ

1 ステップは、レジストレーション 1 回（`fft2` 2 回、`ifft2` 1 回、`fftshift`、最大の位置）。J は区間の外で作っておく。最大の位置は読み戻さないので、区間の中で同期は起きない。比は numpy ÷ Numo（CuPy ÷ Cumo）で、1 を超えれば Ruby 側が速い。後ろの n/10 は、10 ラウンドのうち比が 1 を超えたラウンドの数。

- `rfft2` は `fft2` の 0.42 倍（Numo）と 0.38 倍（numpy）の時間で済む。
- n = 256 の Numo は、プロセスごとに 2.50 ms 前後と 3.45 ms 前後の 2 群に分かれた（Numo の系列で 1/10、対照の系列で 4/10 が遅い群）。中央値は速い群に入る。遅い群のラウンドでも numpy が速いので、比の向きは変わらない。D の `rfft_pow2` と `fft_pow2` でも、Numo に同じ 2 群が出ている。

#### Cumo が遅い理由（`fft2`、n = 1024、fp32、10/18 の `e9ae5d76`）

nsys で、`--inner` 1000 と 3000 の差から、1 ステップのカーネルを数えた（`docs/method.md` の数え方）。どちらも GPU の時間で決まっていて、カーネルの時間の合計は Cumo が 284 µs、CuPy が 185 µs だった（計測の表は 0.289 ms と 0.204 ms）。

| カーネル | Cumo（本数、µs） | CuPy（本数、µs） |
|---|---|---|
| cuFFT（`regular_fft`、`vector_fft`） | 6、116.8 | 6、97.6 |
| 実数 → 複素数の変換 | 3、59.2 | 2、18.5 |
| 割り算（`cross / cross.abs` と、`ifft2` の 1/n²） | 2、33.9 | 2、22.1 |
| 積、`conj`、`abs` | 3、42.5 | 3、29.3 |
| `real` | 1、8.5 | 0（ビュー） |
| `fftshift`（4 ブロックのコピー） | 4、7.9 | 4、9.4 |
| 最大の位置 | 2、14.7 | 3、8.3 |

差の 98 µs は、3 つに分かれる。

1. **複素数を実数で割ると、Cumo は実数を複素数に変換してから割っていた。** `SComplex / SFloat` を切り出して nsys で見ると、1 回ごとに `store_sfloat`（変換）と `div` の 2 本が走った。CuPy は、複素数と実数を混ぜて割るカーネル（`cupy_true_divide__complex64_float32_complex64`）を 1 本だけ使う。変換の 1 本で約 20 µs。0.14.0 までは、割り算に限らず、同じ精度の複素数と実数の + − × ÷ が、どちらの順序でも変換していた。cumo 0.14.1（#632）で、この変換は無くなった。ただし、n = 1024 の `fft2` の 1 ステップは速くならなかった（[cumo-0.14.1.md](cumo-0.14.1.md)）。
2. **Cumo の `real` は、コピーを作る**（Numo と同じ挙動）。CuPy はビューを返す。約 8.5 µs。
3. **同じカーネルでも、Cumo のほうが遅い。** cuFFT のカーネルは同じ種類が同じ本数なのに、117 µs と 98 µs だった。変換のカーネル 1 本あたりも、Cumo の約 20 µs に対し、CuPy は約 9 µs だった。Cumo の一時配列は、Ruby の GC が回るまでメモリプールに戻らない（cumo #221、#222）。そのため毎ステップ新しいメモリを使い、L2 キャッシュに載ったまま回らないと見ている。同じプロセスで、一時配列をすぐ `free` する版と比べると、次のようになった（単発、3 回の交互）。

| n（fp32） | 今の版 | すぐ `free` する版 | CuPy（表） |
|---|---|---|---|
| 1024 | 0.280〜0.287 ms | 0.253〜0.264 ms | 0.204 ms |
| 2048 | 2.29〜2.30 ms | 1.79〜1.80 ms | 1.59 ms |
| 4096 | 9.31〜9.38 ms | 9.33〜9.48 ms | 8.50 ms |

すぐ解放すると、CuPy との差のうち、n = 2048 では 7 割、1024 では 3 割が埋まる。4096 では変わらない。配列が L2 に収まらない大きさでは、どのみちメモリから読むためと見ている。4096 で残る 0.9 ms は、1 と 2 の 2 本（読み書きで合わせて約 384 MB）で説明がつく大きさ。どれも推定で、L2 の当たり外れを直接は数えていない。

### CPU と GPU の逆転

CPU の表と GPU の表は別の回なので、比は出さない。fp64 の `fft2` の中央値を、それぞれの表から読む。

- **測った範囲（n ≥ 256）では、どのサイズでも GPU が速い。** n = 256 で、numpy 2.26 ms に対して CuPy 0.147 ms、Numo 2.52 ms に対して Cumo 0.180 ms。逆転は n = 256 より下にある。
- n = 4096 では、numpy 1263 ms と CuPy 34.2 ms、Numo 3007 ms と Cumo 39.8 ms になる。
