# G. 相関とスペクトル推定

正弦波（f₀ = 1184 Hz、振幅 A = 1）と白色雑音（σ = 0.5）を足した実信号 x を、サンプリング周波数 fs = 8192 Hz で扱う。長さは 3 系統で、2 の冪（短い x が 256、長い x が 65536）、2・3・5・7 の積（420 と 75600 = 2⁴·3³·5²·7）、素数（257 と 65537）。2026-10-18、cumo master `e9ae5d76`（`vendor/cumo-e9ae5d76/`）、CuPy 14.2.0、numpy 2.5.3、scipy 1.18.1、numo-pocketfft 0.7.0、RTX 5070 Ti Laptop（12 GB）。

## 経路と関門

| 関門 | 比べるもの |
|---|---|
| `<系統>.short.direct` | Wiener–Khinchin の自己相関 `irfft(\|rfft(x, n: 2N)\|², n: 2N)[0...N]` と、O(N²) の直接の和（短い x だけ。fixture に入れてある） |
| `<系統>.<長さ>.fftconvolve` | 同じ自己相関を `fftconvolve(x, x.reverse)[N − 1...2N − 1]` から |
| `<系統>.<長さ>.complex` | 同じ自己相関を複素数の `ifft(\|fft(x, n: 2N)\|²).real[0...N]` から |
| `<系統>.<長さ>.hfft` | 巡回の自己相関 r_c の前半に `hfft(…, n: N)` を掛けた実数のスペクトルの前半と、`\|rfft(x)\|²` |
| `<系統>.<長さ>.ihfft` | `ihfft(hfft(h))` と h（h は r_c の前半） |
| `<系統>.welch.peak_frequency` | Welch 法（L = 256、周期的な Hann 窓、50% の重なり、片側の密度）のピークの周波数（`rfftfreq(L, d: 1 / fs)`）が f₀ に等しい |
| `<系統>.welch.peak_height` | ピークの高さと、A²/2 · (Σw)² / (fs Σw²) + 2σ²/fs との相対差が 10% 以下 |
| `<系統>.welch.noise_floor` | ピークの両側 4 ビンと DC、Nyquist を除いた平均と、2σ²/fs との相対差が 10% 以下 |

`<長さ>` は `short` と `long`。数値の関門の tol は、fp64 で 1.5e-14、fp32 で 6e-6 にした。fp64 は Numo で測った最大（1.48e-15、素数長の `ihfft`）の 10 倍、fp32 は numo-pocketfft に単精度が無いので、numpy、CuPy、Cumo の最大（5.94e-7、素数長の `complex`）の 10 倍。計画の (1) は 1e-10 としていたが、それより厳しい。

計画からの読み替えが 2 つある。

- **`hfft` には、線形の自己相関 r ではなく、巡回の自己相関 r_c[k] = r[k] + r[N − k]（r_c[0] = r[0]）を渡す。** 計画は「`hfft(r[0..N/2], n: N)` が `|rfft(x)|²` と一致」としていた。しかし長さ N の `|rfft(x)|²` の逆変換は、巡回の自己相関になる。r_c は実数で偶対称なので、前半から `hfft` で実数のスペクトルが出る。
- **雑音床は 2σ²/fs にした。** 計画は、ピークの高さを片側の式（A²/2 · 窓の係数）で、雑音床を両側の値（σ²/fs）で書いていた。片側の密度（scipy の `welch` の既定と同じ）にそろえると、雑音床は 2σ²/fs になる。

Welch のセグメントは、L の倍数から始まるもの（0、L、2L …）と、L/2 から始まるもの（L/2、3L/2 …）の 2 組に分け、それぞれを `reshape` で 2 次元にしてから、`rfft(…, axis: -1)` を 1 回ずつかける。平均を取るので、セグメントの順番は結果に効かない。Python も同じ手順で書いた（`cupyx.scipy.signal.welch` は使わない）。

Welch（L = 256）は、7 通りとも同じ値になる。ピークの周波数は 3 系統とも 1184 Hz で、f₀ のビンに一致した。

| 系統 | セグメント数 | ピークの高さの相対差 | 雑音床の相対差 |
|---|---|---|---|
| 2 の冪（65536） | 511 | 1.21e-4 | 7.29e-3 |
| 混合基数（75600） | 589 | 7.92e-3 | 5.99e-3 |
| 素数（65537） | 511 | 1.65e-3 | 6.53e-3 |

- 4 実装とも、fp64 と fp32 で 36 個の関門がすべて通る。`values`（長い x のエネルギー r[0]、Welch のピークの周波数、高さ、雑音床）は、fp64 の 4 実装で 1e-9 の内側、fp32 の 3 実装で 1e-3 の内側に揃う（`script/compare_gates.rb`）。
- **素数長（Bluestein）でも、誤差は 2 の冪の 2〜3 倍に収まる。** fp64 の最大は、CuPy と Cumo の `complex` の 1.81e-15（長さ 514 の複素変換。257 の 2 倍）と、numpy の `ihfft` の 1.85e-15。
- CuPy と Cumo は同じ cuFFT を呼ぶので、ほとんどの値がビットまで同じになる。違うのは、混合基数の `complex` と `ihfft`（fp64 と fp32）。
- numpy の fp32 の `complex` は 0 になる。numpy は単精度の入力を単精度で変換する（`fft` の倍精度との差は 3.8e-8）。それでも、実数の入力の `fft` と `ifft` は、`rfft` と `irfft` の経路とビットまで同じ結果を返した。numpy が実数の入力の `fft` を `rfft` から組み立てているためと見ている（確かめていない）。numpy の fp32 の `hfft` が 1e-9 前後と小さいのも、同じ理由かもしれない。
- Numo シムと `Cumo::FFT` の直接比較（`test/test_parity.rb` の G の呼び出し 52 種）の差は、最大 1.44e-15（長さ 65536 の実数の入力の `ifft`）。

## 速さ

ステップは 3 種類。`wk_<系統>` は、長い x の Wiener–Khinchin の自己相関 1 回（長さ 2N の `rfft` と `irfft`、絶対値の 2 乗、前半の切り出し）。2·65537 = 131074 は素因数 65537 を持つので、素数の系統の変換は Bluestein を通る。`welch<L>_<系統>` は、長い x の Welch の PSD 1 回（セグメントの 2 組の `reshape`、窓、`rfft(…, axis: -1)` 2 回、絶対値の 2 乗、平均、片側の係数）。変換の長さは L（どれも 2 の冪）で、系統によって変わるのはセグメントの数（L = 256 で 511〜589 本）だけ。`welch_cycle` は、L = 128〜4096 の 6 通りと 3 系統の 18 通りの Welch を、1 ステップで順に回す。使うプランは約 20 種類で、キャッシュ（16 枚）から溢れる。比は numpy ÷ Numo（CuPy ÷ Cumo）で、1 を超えれば Ruby 側が速い。後ろの n/10 は、10 ラウンドのうち比が 1 を超えたラウンドの数。

- **Wiener–Khinchin の自己相関は、Numo が numpy より 1.17〜1.35 倍速い。** 1 次元の長い `rfft` と `irfft` では、numo-pocketfft（C 版）が numpy（C++ 版）より速い。D の手書きの経路（n = 10⁵ の `rfft_exact` で 1.12）と同じ向き。素数長（Bluestein）は、2 の冪の 7〜8 倍の時間がかかる。
- **Welch は、numpy が 2〜4 倍速い。** 短い変換をたくさん並べる形で、Numo シムは `rfft` の 1 回ごとに、numo-pocketfft の C の関数に行列を渡す（`ext_rfft` は行ごとに変換する）。差が変換そのものか、窓や絶対値の 2 乗や平均のような要素ごとの演算か、どちらにあるかは確かめていない。
- `wk` の 2 の冪の Numo は、プロセスごとに 2.06〜2.10 ms と 2.31〜2.35 ms の 2 群に分かれた（Numo の系列で 5/10 が遅い群）。中央値の 2.20 ms は 2 群の間に落ち、どちらの群の値でもない。遅い群でも numpy の 2.63〜2.72 ms より速いので、比の向きは変わらない。D と E の Numo でも、同じ 2 群が出ている。
- 初回は、Numo が定常の 2.1 倍（`wk`、素数）と 2.8 倍（`welch1024`）。numo-pocketfft はプランを毎回作るので、Numo の初回と定常の差はプランの生成ではない。

- **Welch は、どの長さでも Cumo が 1.55〜1.63 倍速い。** 1 ステップは L や系統によらず 0.095 ms 前後（CuPy は 0.152 ms 前後）で、時間はカーネルの起動の手間で決まっている。nsys で数えると（L = 256、2 の冪、`--inner` 1000 と 3000 の差）、1 ステップに Cumo は 33 本（cuFFT 2 本を含む）、CuPy は 24 本のカーネルを起動し、カーネルの時間の合計はどちらも 25 µs 前後だった。1 本あたりにすると、Cumo が約 2.9 µs、CuPy が約 6.3 µs になる。Cumo の本数が多いのは、絶対値の 2 乗の `z.real` と `z.imag` がコピーを作るため（4 本ずつ。CuPy はビュー）。
- **キャッシュを溢れさせる条件でも、Cumo が 1.55 倍速い。** nsys では、1 ステップに両者とも 20 枚のプランを作って捨てていた（`cuModuleLoadData` と `cuModuleUnload` が 20 回ずつ。cuFFT がプランごとにモジュールを読む）。Cumo はプランを捨てる前に、そのプランの最後の変換を待つ `cudaEventSynchronize` を 20 回入れるが、差を逆転させるほどには効いていない。差の 2.4 ms のうち約 1 ms は、Welch 1 回分の起動の手間の差（0.057 ms × 18 回）で説明がつく。残りは、プランを作り直す手間の差と見ている（確かめていない）。計画は「LRU の破棄の手間の差が出る」と見ていたが、この条件では起動の手間の差のほうが大きかった。
- **自己相関は、fp32 で互角、fp64 で CuPy が 0.6〜6% 速い。** 素数長（Bluestein）でも比は 2 の冪と同じくらいで、計画の見どころの「比が他の長さと同じなら、差はラッパーで説明できる」に当たる。fp64 の 2 の冪と混合基数で CuPy が速いのは、E と同じく、`real` と `imag` のコピーと、一時配列のメモリの使い回しの差と見ている（G では確かめていない）。
- 初回は、Cumo が CuPy の 4.9 倍（`wk`）と 13 倍（`welch1024`）遅い。D と同じく、要素ごとの演算のカーネルの読み込みが入っていると見ている（G では確かめていない）。Welch は使う演算の種類（`cos`、`seq`、`fill`、`sum` など）が多いので、読み込む族も多い。

### CPU と GPU の逆転

CPU の表と GPU の表は別の回なので、比は出さない。fp64 の `wk` と、Welch（CPU は fp64、GPU は fp32）の中央値を、それぞれの表から読む。

- **自己相関（長さ 65536〜75600）は、GPU が 13〜36 倍速い。** 2 の冪で numpy 2.65 ms と CuPy 0.099 ms、Numo 2.20 ms と Cumo 0.105 ms。素数長で numpy 19.6 ms と CuPy 0.540 ms、Numo 16.8 ms と Cumo 0.544 ms。
- **Welch は、Python では GPU が 1.8〜3 倍速く、Ruby では 8〜13 倍速い。** numpy は 0.28〜0.46 ms、CuPy は 0.15 ms 前後。Numo は 0.78〜1.26 ms、Cumo は 0.095 ms 前後。ただし dtype が違う（CPU は fp64、GPU は fp32）。Welch の GPU の時間は起動の手間で決まっているので、fp64 でもほぼ変わらないと見ている（測っていない）。
- 測った長さはどれも、GPU が速い側にある。逆転は、ここより短い信号にある。
