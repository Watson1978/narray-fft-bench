# D. 多倍長整数の乗算

2 つの n 桁の整数を、基数 B の桁の列（下位の桁から）の畳み込みで掛ける。畳み込みの係数を `rint` で丸め、ホストで繰り上げて、Ruby の `Integer`（Python は `int`）の積と桁ごとに比べる。2026-10-17、cumo master `e9ae5d76`（`vendor/cumo-e9ae5d76/`）、CuPy 14.2.0、numpy 2.5.3、scipy 1.18.1、numo-pocketfft 0.7.0、RTX 5070 Ti Laptop（12 GB）。

## 経路

| 経路 | 呼び出し | 変換の長さ m |
|---|---|---|
| `fftconvolve` | `XFT.fftconvolve(a, b)`（Python は `xsig.fftconvolve(a, b, mode="full")`） | Numo は 2n − 1 のまま複素数の `fftn`。scipy、CuPy、cumo は 2·10ᵏ に伸ばして `rfft` |
| `rfft_pow2` | `irfft(rfft(a, n: m) * rfft(b, n: m), n: m)` | 2n − 1 以上の 2 の冪 |
| `rfft_exact` | 同じ | 2n − 1 |
| `fft_pow2` | `ifft(fft(a, n: m) * fft(b, n: m))` の実部 | 2 の冪 |
| `fft_exact` | 同じ | 2n − 1 |

2n − 1 は、どのサイズでも大きな素因数を持つ（n = 10³ から順に 1999、7·2857、199999、17·71·1657、19999999、3·13·1025641）。`_exact` の経路は、pocketfft でも cuFFT でも Bluestein を通る。

## 関門

- `<経路>.error`: 丸める前の係数と、厳密な係数 `exact` との差の最大値が **0.5 未満**（`Gates.lt`）。`exact` は、`script/make_fixtures.rb` が Ruby の `Integer` で求めて fixture に入れてある（桁を 64 ビットの枠に詰めて掛ける Kronecker 置換）。0.5 未満なら、すべての係数が正しい整数に丸まる。fp32 では誤差がちょうど 0.5 になり、偶数丸めで外れる例があった（numpy の `b10_n1e5` の `rfft_pow2`、54 桁）ので、「以下」ではなく「未満」にした。
- `<経路>.mismatches`: 繰り上げたあとの 2n 桁のうち、`Integer` / `int` の積と違う桁の数が 0。積は関門を回すたびに、各言語の多倍長整数で計算する。
- `paths.spread`: 丸める前の係数の、経路どうしの差の最大値が 0.5 未満（計画の関門 (2)）。
- `values`: 1 番目の経路（`fftconvolve`）の積の桁数と、桁の和。

完全一致の題材なので、tol は持ち込まない。

- **誤差は n にほぼ比例して伸びる。** 係数の最大値も n に比例するので、相対誤差はサイズによらずほぼ一定になる。Numo の `rfft_pow2` で 7.5e-16（倍精度の ε の 3.4 倍）、cuFFT の `rfft_exact` で 2.8e-15。
- **B = 10⁴ の倍精度で桁が全部合う上限は、n = 10⁷（10 進で 4×10⁷ 桁）の前後にある。** 長さを 2 の冪にした経路は、4 実装とも 10⁷ で全部合う。2×10⁷ では、Numo は 2 の冪の 2 経路とも合い、numpy は `rfft_pow2` だけが合う。cuFFT は 2 の冪の 2 経路とも 1〜235 桁が外れる。計画は「n = 10⁷ より前に FFT の誤差で崩れるはず」と見ていたが、2 の冪なら 10⁷ でも崩れなかった。
- **2n − 1 の長さ（Bluestein）では、cuFFT が先に崩れる。** cuFFT は n = 10⁷ で約 4000〜7000 桁が外れる。pocketfft（Numo、numpy）は 10⁷ では全部合い、2×10⁷ で崩れる。
- `fftconvolve` は、Numo では 2n − 1 のままなので `_exact` と同じ値になる。scipy、CuPy、cumo は 2·10ᵏ（2 と 5 だけの積）に伸ばすので、2 の冪の経路に近い振る舞いになり、10⁷ では全部合い、2×10⁷ で崩れる。
- **関門 (2)（経路間の差）は、桁が崩れるより先に落ちる。** numpy の n = 10⁷ は、5 経路とも桁が全部合っているのに、差が 0.562 になった。各経路の誤差が 0.5 近くまで来ると、2 つの経路が逆向きにずれるため。計画どおり、関門は緩めない。
- CuPy と Cumo は同じ cuFFT を呼ぶので、誤差の多くが同じ値になる。ただし、経路とサイズによっては違う（n = 10⁴ の `fft_exact`、10⁵ の `rfft_pow2`、10⁶ の `rfft_exact`、2×10⁷ の `rfft_pow2` など）。原因は確かめていない。
- **CuPy は、n = 10⁷ の fp64 で 5 経路を 1 プロセスで回すと、12 GB の GPU のメモリが足りなくなる。** プランキャッシュが、プランごとの cuFFT の作業領域を持ち続けるため（[cupy-notes.md](../cupy-notes.md)）。上の CuPy の 10⁷ と 2×10⁷ の行だけは、経路ごとに別のプロセスで測った（`python/problems/bignum_mul.py` の `coefficients` を 1 経路だけ呼ぶ一時スクリプト。桁の不一致は、`exact` を繰り上げたものと比べた。他の 3 実装では、これが `int` の積と一致する）。そのため `paths.spread` が無い。2×10⁷ の `rfft_exact` は、単独で回しても `CUFFT_ALLOC_FAILED` になる。Cumo は 2×10⁷ まで、5 経路を 1 プロセスで回せる。

## 速さ

1 ステップは、係数を出して `rint` で丸めるまで。繰り上げはホストの Ruby / Python の処理で、FFT ではないので含めない。比は numpy ÷ Numo（CuPy ÷ Cumo）で、1 を超えれば Ruby 側が速い。後ろの n/10 は、10 ラウンドのうち比が 1 を超えたラウンドの数。

#### 初回の内訳

内訳の数字は、1 プロセスずつ 1〜3 回測った値で、表の数字ではない。

- cumo は、CUDA のモジュールの遅延読み込み（`CUDA_MODULE_LOADING=LAZY`、cumo #590）を既定にしている。要素ごとの演算のカーネルは、型ごとに演算の族に分けてある（#583、#610）。族の中の最初のカーネルを呼んだときに、その族のモジュールが読み込まれる。`FFTBench.prime`（長さ 3 の複素 `fft`）は、初回の条件が使う族の多くを読まない。
- `prime` のあとに、演算を長さ 8 で 1 回ずつ呼ぶと、初めての族で時間がかかる。SFloat の `seq` が 13.5 ms、比較（`> 1`）が 6.8 ms、`sum` が 29.4 ms、範囲の `dup` が 3.2 ms だった。`SComplex.cast` は 7.8 ms、SComplex どうしの積は 12.9 ms で、積の 2 回目は 0.021 ms になる。同じ族の 2 つ目の演算（`seq` のあとの `* 2`、`/ 2`、`rint`）は、0.1 ms 未満で済む。CuPy の積の初回は 0.2 ms だった。CuPy は、カーネルを 1 本ずつディスクのキャッシュ（`~/.cupy/kernel_cache` の cubin）から読む。
- `CUDA_MODULE_LOADING=EAGER` にすると、手間が初回から起動へ移る。`prime` は 27 ms から 1.18 s に延びる。一方、初回の `fftconvolve` は 36.2 ms から 7.0 ms（CuPy は 4.3 ms）に、`rfft_exact` は 41.5 ms から 12.7 ms（CuPy は 10.1 ms）に縮む。
- **プランの生成そのものは、Cumo と CuPy で同じくらい。** カーネルを読み込んだあとに、新しい長さの `rfft` と `irfft` を 1 回ずつ呼ぶと、どちらもプランを 1 枚ずつ作る。長さ 200000 では Cumo 1.7 ms と 1.9 ms、CuPy 1.3 ms と 1.7 ms だった。長さ 199999（Bluestein）では Cumo 6.4 ms と 4.2 ms、CuPy 5.1 ms と 5.2 ms だった。
- 初回の表の値は、計画の定義（プロセスで最初の 1 回。プランの生成と作業領域の確保を含む）どおりに測ったもので、Ruby の利用者が新しいプロセスで最初に払う時間でもある。cuFFT のプランの生成だけを比べたいときは、上の内訳を見る。`FFTBench.prime` は変えていない。

### CPU と GPU の逆転

CPU の表（2026-10-17）と GPU の表（2026-10-18）は別の回の計測なので、比は出さない。fp64 の `fftconvolve` の中央値を、それぞれの表から読む。

- **Python では、n = 10³ と 10⁴ の間で GPU が CPU を抜く。** n = 10³ では numpy 0.033 ms、CuPy 0.061 ms で、CPU が速い。n = 10⁴ では numpy 0.192 ms、CuPy 0.124 ms で、GPU が速い。
- **Ruby では、n = 10³ で既に GPU が速い。** n = 10³ で Numo 0.196 ms、Cumo 0.056 ms だった。Numo の `fftconvolve` が、長さを伸ばさずに 2n − 1 のまま変換するため（CPU の節）。n = 10⁶ では Numo 859 ms、Cumo 2.21 ms になる。
