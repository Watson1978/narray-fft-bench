# C. 3 次元の Poisson 方程式（ガウス電荷のポテンシャル）

辺 L = 1 の周期箱の中心に、総電荷 1 のガウス電荷 ρ = (2πσ²)^{−3/2} exp(−r²/2σ²)（σ = L/16）を置き、∇²φ = −ρ を φ̂ = ρ̂ / k²（k = 0 は 0。周期系では平均を落とす）で解く。2026-10-18、cumo 0.14.0（`vendor/cumo-0.14.0/`。GPU の表は 2026-10-22 に cumo 0.14.1 で測り直した）、CuPy 14.2.0、numpy 2.5.3、numo-pocketfft 0.7.0、RTX 5070 Ti Laptop（12 GB）。

## 経路

| 経路 | 呼び出し |
|---|---|
| `rfftn` | `irfftn(rfftn(ρ) / k², s: [N, N, N])`（最後の軸が片側） |
| `fftn` | `ifftn(fftn(ρ) / k²).real` |
| `axes01` | `irfftn(rfftn(ρ, axes: [0, 1]) / k², s: [N, N], axes: [0, 1])`。各 z 断面の 2 次元の Poisson で、末尾でない軸の変換を踏む |

波数は `fftfreq(N, d: L/N)` の 2π 倍（最後の軸は `rfftfreq`）。

## 関門

| 関門 | 中身 | tol（fp64 / fp32） |
|---|---|---|
| `reference` | 中心から L/4 未満の 11 点（軸、面の対角、体の対角の向き）での φ の、1 点目との差と、参照の解の同じ差との相対差（max ノルム） | 1e-6（計画のまま） |
| `complex` | `fftn` 経路の φ と `rfftn` 経路の φ | 2.8e-15 / 3.2e-6 |
| `laplacian` | `irfftn(−k² φ̂)` と −(ρ − ρ̄) | 4e-13 / 2.9e-4 |
| `round_trip` | `irfftn(rfftn(ρ), s:)` と ρ（N = 64） | 2.8e-15 / 3.2e-6 |
| `odd_round_trip` | 同じく、奇数の長さを含む 31 × 32 × 33 | 2.8e-15 / 3.2e-6 |
| `axes01` | `fft(rfftn(ρ, axes: [0, 1]), axis: 2)` と `rfftn(ρ, axes: [2, 0, 1])`（どちらも 3 軸の変換で、順番だけが違う） | 2.8e-15 / 3.2e-6 |

`values` は、11 点の φ の幅、軸上の 8 格子点ぶんの差、`s:` を省いて奇数の長さ（最後の軸 33）を往復したときの出力の長さ。`s:` を省くと、出力の長さは 2(m − 1) = 32 になり、もとの 33 に戻らない（計画の「`s:` を省くと奇数長で崩れる」）。4 実装とも 32 になる。

fp64 の tol は、計画に数字があるものはそのまま使い、無いものは Numo で測った最大の 10 倍にした。fp32 は、numpy、CuPy、Cumo の最大の 10 倍。`laplacian` だけ tol が大きいのは、−k² を掛けると、高い波数の丸めの誤差が k² ≈ (π N / L)² ≈ 4×10⁴ 倍になるため。

**参照の解は、無限空間の解ではなく、周期箱の解を Ewald の和で求めた。** 計画は「解析解 erf(r/√2σ) / (4πr) と比べる。周期像と k = 0 の除去は定数を足すだけなので、2 点の差を比べればよい」としていた。しかし平均を落とすことは、一様な背景電荷 −1/L³ を足すことと同じで、ポテンシャルに r²/(6L³) が加わる。周期像は中心で調和な関数を足し、立方の対称性から 2 次の項は消えるが、4 次の項（x⁴ + y⁴ + z⁴ − 3r⁴/5 に比例）が残る。どちらも 2 点の差では消えない。N = 64 の FFT の解と比べると、次のようになった。

| 参照 | `reference` の値 |
|---|---|
| 無限空間の解 erf(r/√2σ) / (4πr) だけ（計画の式） | 1.53e-2 |
| 上に背景の項 r²/(6L³) を足したもの | 1.21e-3 |
| Ewald の和（周期的な点電荷のポテンシャル）に、中心の電荷の広がりの補正 (erf(r/√2σ) − 1) / (4πr) を足したもの | 2.84e-15 |

Ewald の和は、`script/make_fixtures.rb` が Ruby の `Float` で求めて fixture に入れてある（分離の幅 α = 5/L、実空間の像は各軸 ±2、波数は各軸 ±10。どちらの打ち切りも 1e-17 より小さい）。像は中心から 3L/4 以上離れているので、像のガウス電荷は点電荷とみなせる（広がりの補正は 1e-30 より小さい）。ガウス電荷のスペクトルは、Nyquist の波数で exp(−(πNσ/L)²/2) ≈ exp(−79) なので、格子に標本化しても折り返しは無視できる。

- 4 実装とも、fp64 と fp32 で 6 個の関門がすべて通る。`values` は 4 実装で揃う（`script/compare_gates.rb`）。
- fp32 でも、参照の解との差は 2e-7 で、計画の 1e-6 を満たす。
- `axes01` が CPU で 0 になるのは、numo-pocketfft も numpy も、軸ごとに 1 次元の変換を順に掛けるので、軸の順番を変えても同じ計算をするため。GPU では、複数の軸を 1 枚のプランでまとめて変換する（`Cumo::FFT` は 3 軸までを 1 枚にする）ので、軸の順番で丸めの順番が変わる。
- Numo シムと `Cumo::FFT` の直接比較（`test/test_parity.rb` の C の呼び出し 18 種）の差は、最大 4.40e-16（`ifftn`、64³）。

## 速さ

1 ステップは、Poisson の解を 1 回（経路の表の 3 通り）。比は numpy ÷ Numo（CuPy ÷ Cumo）で、1 を超えれば Ruby 側が速い。後ろの n/10 は、10 ラウンドのうち比が 1 を超えたラウンドの数。

- **`axes01`（3 軸のうち 2 軸だけの変換）の 512³ では、Cumo が CuPy の 6.4 倍速い。** 下の「`axes01` で差が出る理由」。
- **`rfftn` は、0.14.1 で CuPy と並んだ。** fp32 の 256³ と fp64 では差が無く（比が 1 をまたぐ）、fp32 の 512³ では Cumo が 2% 速い。128³ の fp32 では、CuPy が 4% 速い。10/18 の 0.14.0 では、CuPy が 1.02〜1.16 倍速かった。
- **`fftn` では、CuPy が 1.1〜1.2 倍速い。** 0.14.0 では 1.2〜1.3 倍だった。`fftn` の残りの差は、実数の入力を複素数にする変換（`Cumo::FFT` の中）と `real` のコピーと見ている（確かめていない）。fp32 の 512³ で比が 1 をまたいだのは、4 ラウンド目に CuPy（48.1 ms）と対照（54.5 ms）が遅かったため。9 ラウンド目にも、Cumo（51.2 ms）と CuPy（42.1 ms）が遅かった。ほかのラウンドは、Cumo が 39.1〜39.7 ms、CuPy が 35.2〜37.8 ms だった。
- **0.14.1 で差が縮んだのは、1/k² を掛けるときの変換が無くなったため。** 512³ の片側スペクトルは 1 本 0.54 GB で、0.14.0 では同じ大きさの変換の一時配列を毎ステップ作っていた。ただし、1 ステップあたりの GC の回数は変わらなかった（[cumo-0.14.1.md](cumo-0.14.1.md)）。差は、変換のカーネルと、その一時配列に初めて書き込む手間の分と見ている（確かめていない）。0.14.0 のときの GC の時間（`GC.stat`、単発）は、`rfftn` の 256³ で 1.06 ms、512³ で 2.60 ms、`fftn` の 256³ で 3.60 ms、512³ で 4.62 ms だった。256³ 以上の配列は 1 本で malloc の上限（16 MB）を超えるので、確保のたびに GC が起きる（B と同じ）。
- 64³ では Cumo が速い（1.19 倍）。呼び出しの手間で決まる大きさ。
- 初回は、Cumo が CuPy の 6.3 倍遅い。D と同じく、要素ごとの演算のカーネルの読み込みが入っていると見ている（C では確かめていない）。

#### `axes01` で差が出る理由（512³、fp32）

nsys で `--inner` 3 と 6 の差を取った。

| | Cumo | CuPy |
|---|---|---|
| 末尾でない軸の扱い | 転置のコピー（`store_sfloat_transpose` 2 本と `store_scomplex_transpose` 2 本で約 5 ms）のあと、連続した配列を変換する | cuFFT の advanced layout（ストライドのある配列のまま）で変換する |
| R2C | `vector_fft_r2c` 1 本、2.8 ms | `regular_fft_r2c` 1 本、42 ms |
| C2R | `vector_fft_c2r` 1 本、1.9 ms | `regular_fft_c2r` 1 本、74 ms |
| C2C（軸 0） | `regular_fft` 2 本、4.0 ms | `regular_fft` 2 本、19 ms |

計画は「`axes: [0, 1]` は cumo も CuPy も swapaxes + コピーに落ちるので、そのコピーの速さの比較になる」と見ていたが、CuPy はコピーをせず、ストライドのまま cuFFT に渡していた。この形（512³、変換する軸がメモリの上で離れている）では、ストライドのまま変換する cuFFT のカーネルが遅く、コピーしてから連続した配列を変換する Cumo のほうが速い。256³ では差が 1.38 倍に縮み、fp64 の 256³ では互角になる。計画の第十一段階の候補（「末尾でない軸の advanced layout（C）」）は、少なくともこの形では、入れると遅くなる側にある。

### CPU と GPU の逆転

CPU の表と GPU の表は別の回なので、比は出さない。fp64 の中央値を、それぞれの表から読む。

- **測った範囲（64³ 以上）では、どこでも GPU が速い。** `rfftn` の 128³ で numpy 20.9 ms と CuPy 1.25 ms、Numo 67.1 ms と Cumo 1.24 ms。256³ では numpy 257 ms と CuPy 10.8 ms、Numo 1193 ms と Cumo 10.7 ms。
- 64³ の fp64 の GPU は測っていない。fp32 の 64³ は Cumo 0.035 ms、CuPy 0.042 ms で、CPU の fp64（numpy 2.71 ms）より 2 桁速い。
