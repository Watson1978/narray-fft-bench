# A. Whisper のメル特徴量（STFT → log-mel）

Whisper の入力の log-mel スペクトログラムを作る。周期的な Hann 窓、中心に合わせて反射でパディングしたフレーム（n_fft = 400、hop = 160）、`rfft(frames, n: 400, axis: -1)` を 1 回、パワー |X|²、[80, 201] のメルフィルタとの `dot`、log10、Whisper の 2 つのクランプ（1e-10 で下を切り、最大値 − 8 で下を切る）、(x + 4) / 4。2026-10-18、cumo 0.14.0（`vendor/cumo-0.14.0/`）、CuPy 14.2.0、numpy 2.5.3、numo-pocketfft 0.7.0、RTX 5070 Ti Laptop（12 GB）。

## 範囲

計画の関門 (1)（narray-llm の Whisper tiny に差し込み、トークン列が完全に一致するか、と encode の速さ）は、このリポジトリの外の作業になる。2026-10-18 のユーザーの判断で、先にこのリポジトリの関門 (2)(3) と計測を済ませ、結果を narray-llm 側のセッションに伝えた。narray-llm 側の判断は、下の「narray-llm での扱い」。

## 入力

- 波形は、narray-llm の Whisper の試験と同じ式（チャープ + 440 Hz、包絡付き、fp32 に丸める）を Numo で計算したもの。メルフィルタは openai/whisper-tiny の `preprocessor_config.json` から取った `script/whisper_mel_filters.json`。
- small は 30 秒（480000 サンプル、3000 フレーム）。計測用に、3 秒（300 フレーム、`f300`）と、30 秒の波形を 10 回つないだ 300 秒（30000 フレーム、`f30000`）を足した。計画の「10 秒分を繰り返す」は 2 通りに読めるが、どちらでも FFT の手間は同じ。

## 手順

narray-llm の `Whisper::Mel`（`lib/narray_llm/models/whisper/mel.rb`）と同じ手順にした。

- 反射のパディングは、両端の 200 サンプルを `reverse` で作る（NArray を添字に使わない）。
- フレーム t は padded[160t, 160t + 400) で、[ブロック数, 160] に `reshape` した配列の 3 つのスライス（160 + 160 + 80）から組む。フレームごとのループは無い。
- DFT の経路は、narray-llm と同じく、cos と sin の [400, 201] の表との行列積 2 回。表の角度は k·n·(−2π/400) で、そのまま作る。
- 「最大値 − 8 で下を切る」クランプは、max(x, m) = (x + m + |x − m|) / 2 の形で、最大値を GPU 上の 0 次元の配列のまま使う。計測のステップの中で読み戻さないため。narray-llm は最大値を読み戻して `clip` に渡している。

## 関門

| 関門 | 中身 | tol（fp64 / fp32） |
|---|---|---|
| `paths` | rfft の経路の log-mel と、DFT の行列積の経路の log-mel の相対差 | 1e-10（計画のまま） / 1.1e-2 |
| `parseval` | 窓を掛けたフレームの Σ\|x\|² と、片側スペクトルから数えた Σ\|X\|² / 400 の相対差 | 1.4e-11 / 4.5e-7 |
| `frequencies` | `rfftfreq(400, d: 1/16000)` と、メルフィルタの列の周波数 40k Hz（k = 0〜200）の相対差 | 0 |

`values` は、フレームの数、log-mel の平均、最大、最小。

fp64 の `paths` は計画の 1e-10 をそのまま使った。ほかは、測った最大の 10 倍（fp64 の `parseval` は Numo の 1.33e-12、fp32 は numpy、CuPy、Cumo の最大）。

**fp32 の `paths` の tol が 1.1e-2 と大きいのは、DFT の表の誤差を測っているため。** 角度 k·n·(2π/400) は最大で約 1253 rad になり、fp32 ではその丸めが 1e-4 rad ほどになる。fp64 の rfft の log-mel を正しい値として比べると、次のようになった（numpy、fp32、30 秒）。

| fp32 の経路 | fp64 の rfft の log-mel との相対差 |
|---|---|
| rfft | 9.47e-8 |
| DFT の行列積（narray-llm と同じ表） | 1.02e-3 |
| DFT の行列積（角度を k·n mod 400 に畳んでから作った表） | 5.59e-5 |

**narray-llm の今の log-mel（fp32 の DFT の表）は、rfft にすると 1 万倍正確になる。** 角度を k·n mod 400 に畳むだけでも 18 倍よくなる。これがトークン列を変えるかは、narray-llm の Whisper で確かめないと分からない（計画の関門 (1)）。

## 関門の値（30 秒、3000 フレーム）

| | Numo | numpy | CuPy | Cumo | numpy fp32 | CuPy fp32 | Cumo fp32 |
|---|---|---|---|---|---|---|---|
| `paths` | 2.48e-12 | 2.48e-12 | 2.47e-12 | 2.47e-12 | 1.02e-3 | 1.03e-3 | 1.03e-3 |
| `parseval` | 1.33e-12 | 1.58e-16 | 1.58e-16 | 1.58e-16 | 4.08e-8 | 4.42e-8 | 4.08e-8 |
| `frequencies` | 0 | 0 | 0 | 0 | 0 | 0 | 0 |

- 4 実装とも、fp64 と fp32 で 3 個の関門がすべて通る。`values`（log-mel の平均 −0.2805、最大 1.549、最小 −0.4507）は、fp64 の 4 実装で 1e-9 の内側、fp32 の 3 実装で 1e-3 の内側に揃う（`script/compare_gates.rb`）。
- fp64 の `paths` の 2.5e-12 も、DFT の表の角度の丸め（fp64 で 1253 rad の 1 ulp は 2.3e-13）から来ていると見ている。
- Numo の `parseval` だけが 1.33e-12 で、ほかの 3 実装は 1.58e-16。120 万個の 2 乗の和を、Numo の `sum` が順に足していくためと見ている（numpy は 2 分割で足し、GPU は木の形で足す。確かめていない）。
- Numo シムと `Cumo::FFT` の直接比較（`test/test_parity.rb` の A の呼び出し 3 種）の差は、最大 3.76e-16（`rfft`、[3000, 160] の行を n: 400 まで 0 で伸ばしたもの）。

## 速さ

1 ステップは、波形から log-mel を 1 回作る（パディング、フレーム、窓、`rfft` か DFT の行列積、パワー、メルとの `dot`、log10、クランプ）。`rfft` は rfft の経路、`dft` は narray-llm と同じ DFT の行列積の経路。比は numpy ÷ Numo（CuPy ÷ Cumo）で、1 を超えれば Ruby 側が速い。後ろの n/10 は、10 ラウンドのうち比が 1 を超えたラウンドの数。

### CPU（Numo / numpy、fp64）

2026-10-18 15:24〜15:38、`bench/run.sh`（10 ラウンド、対照系列付き）。**行列積（`dot`）は、Numo（numo-linalg-alt 0.10.1）も numpy も OpenBLAS を通り、既定の設定のまま複数のスレッドで動く**（この機械は 24 スレッド）。FFT（pocketfft）は、どちらも 1 スレッド。BLAS を 1 スレッドにすると（`OPENBLAS_NUM_THREADS=1`、単発、30 秒）、numpy の `dft` は 8.58 ms から 23.0 ms に、Numo の `dft` は 15.7 ms から 24.4 ms に延び、Numo の `rfft` は 18.0 ms から 18.8 ms とほとんど変わらなかった。

| 条件 | Numo (ms) | numpy (ms) | numpy ÷ Numo |
|---|---|---|---|
| `rfft`、300 フレーム | 1.62 | 0.836 | 0.518 0/10 |
| `rfft`、3000 フレーム | 18.2 | 8.30 | 0.451 0/10（Numo が 2 群に分かれる） |
| `rfft`、30000 フレーム | 336 | 114 | 0.338 0/10 |
| `dft`、300 フレーム | 1.35 | 1.29 | 0.956 3/10（またぐ） |
| `dft`、3000 フレーム | 14.4 | 9.13 | 0.632 0/10 |
| `dft`、30000 フレーム | 286 | 115 | 0.400 0/10 |
| 初回、`rfft`、3000 フレーム | 55.1 | 12.2 | 0.221 0/10（対照が 1 をまたがない） |

- **numpy が Numo より 1.6〜3.0 倍速い（300 フレームの `dft` だけは互角）。** `rfft` の経路では、どのフレーム数でも numpy が速い。
- **CPU では、DFT の行列積の経路が rfft の経路と同じくらいか、速い。** Numo では、3000 フレームで `rfft` 18.2 ms に対して `dft` 14.4 ms。行列積が BLAS の複数のスレッドで動き、rfft は 1 スレッドのため。
- 初回は、対照 ÷ Numo が 0.911 0/10 で、1 をまたがなかった（対照の系列が 47.7〜53.1 ms、Numo の系列が 50.1〜73.3 ms）。規則どおり、この条件は README に載せない。
- 3000 フレームの `rfft` の Numo は、17.0〜17.4 ms と 18.8〜19.3 ms の 2 群に分かれた（D〜F の Numo と同じ）。どちらの群でも numpy の 7.8〜9.0 ms より遅い。300 フレームの `dft` は、BLAS のスレッドのせいか、Numo が 1.07〜1.39 ms とばらついた。

### GPU（Cumo / CuPy）

2026-10-18 15:38〜15:53、`bench/run.sh`（10 ラウンド、対照系列付き）、cumo 0.14.0。クロックは D〜C と同じ固定のまま（始める前のアイドルの SM が 2797 MHz）。cumo 側のセッションは GPU を使っていなかった。対照 ÷ Cumo は、すべての条件で 1 をまたいだ。幅が 5% を超えた系列は生の値をラウンド順に見て、2 つの群には分かれていなかった。

| 定常 | Cumo (ms) | CuPy (ms) | CuPy ÷ Cumo |
|---|---|---|---|
| `rfft`、300 フレーム、fp32 | 0.099 | 0.154 | 1.557 10/10 |
| `rfft`、3000 フレーム、fp32 | 0.219 | 0.155 | 0.710 0/10 |
| `rfft`、30000 フレーム、fp32 | 2.93 | 1.50 | 0.512 0/10 |
| `dft`、300 フレーム、fp32 | 0.090 | 0.154 | 1.709 10/10 |
| `dft`、3000 フレーム、fp32 | 0.242 | 0.248 | 1.030 10/10 |
| `dft`、30000 フレーム、fp32 | 2.73 | 2.44 | 0.891 0/10 |
| `rfft`、3000 フレーム、fp64 | 0.752 | 0.692 | 0.919 0/10 |
| `dft`、3000 フレーム、fp64 | 3.18 | 3.18 | 0.998 4/10（またぐ） |

| 初回 | Cumo (ms) | CuPy (ms) | CuPy ÷ Cumo |
|---|---|---|---|
| `rfft`、3000 フレーム、fp32 | 128 | 72.9 | 0.567 0/10 |

- **Whisper の 30 秒（3000 フレーム、fp32）の rfft の経路は、CuPy が 1.41 倍速い**（Cumo 0.219 ms、CuPy 0.155 ms）。300 フレームでは、呼び出しの手間で決まるので Cumo が 1.56 倍速い。
- **CuPy では rfft の経路が DFT の行列積より速い（3000 フレームで 0.155 ms と 0.248 ms）が、Cumo ではほとんど変わらない（0.219 ms と 0.242 ms）。** 30000 フレームでは、Cumo は DFT の行列積のほうが速い（2.73 ms と 2.93 ms）。
- Cumo の rfft の経路が遅いのは、ほかの題材と同じく Ruby の GC のため。1 ステップあたりの GC の時間（`GC.stat`、単発）は、3000 フレームで 0.11 ms（1 ステップ 0.20 ms のうち）、30000 フレームで 2.62 ms（2.77 ms のうち）だった。DFT の行列積の経路でも、30000 フレームで 2.24 ms（2.37 ms のうち）が GC。30000 フレームの fp32 のフレームの行列は 1 本 48 MB で、malloc の上限（16 MB）を 1 本で超える（B と同じ）。
- 初回は、Cumo が CuPy の 1.8 倍遅い。D と同じく、要素ごとの演算のカーネルの読み込みが入っていると見ている（A では確かめていない）。

**narray-llm の Whisper への差し込みについて:** Cumo で log-mel を rfft の経路に替えると、3000 フレームの 1 回は 0.242 ms から 0.219 ms になる（1.1 倍）。速さの得は小さいが、fp32 の精度は 1 万倍よくなる（1.02e-3 から 9.5e-8。上の「関門」）。計画の見どころ（「narray-llm の Whisper encode で PyTorch に 15% 負けている件の一部がメル計算なら、ここで取り返せる」）については、log-mel 全体が 0.24 ms なので、encode 全体の 15% を取り返す大きさにはならないと見ている（encode の時間は測っていない）。

## narray-llm での扱い

2026-10-18、narray-llm 側のセッションが、この結果をもとに次のように決めた（narray-llm のコミット `2faa1db`）。

- **DFT の表の角度を k·n mod 400 に畳んでから作るように直した。** 添字の積を `Int32` で取って 400 で割った余りを角度にする。変わったのは読み込み時に作る表だけ。narray-llm の `test_whisper_mel` の参照（feature extractor）との最大差は、Numo fp32 で 1.593e-3 から 8.37e-5 に、Cumo fp32 で 1.606e-3 から 6.60e-5 になった。
- **トークン列は fixture と完全に一致したまま** で、Whisper の試験 4 ファイルが Numo と Cumo の両方で通った。
- **rfft への置き換えは見送った。** cumo 0.14.0 と numo-pocketfft への依存が増えるわりに、GPU ではほぼ速くならず（上の 0.242 ms と 0.219 ms）、CPU では遅くなる（BLAS の行列積のほうが速い）ため。
- narray-llm の文書は、誤差の原因を「fp32 の行列積」としていたが、位相の表の丸めだったと書き直した。

計画の関門 (1) は、rfft を差し込む形では行わないことになった。encode の速さも測っていない。
