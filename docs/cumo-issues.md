# cumo に戻すもの

計画の第十一段階。7 題材と `Cumo::Pocketfft` の互換の試験で見つけたものを、cumo 0.14.0 に対してまとめる。2026-10-22 に出た 0.14.1 で、3 番が直った（[results/cumo-0.14.1.md](results/cumo-0.14.1.md)）。2026-11-02 に出た 0.15.0 で、2 番のうち縮約の分が縮んだ（[results/cumo-0.15.0.md](results/cumo-0.15.0.md)）。**正しさの問題は見つかっていない。** ここにあるのは性能の差と、その原因の仮説。cumo 側のセッションには 2026-10-18 に、題材ごとに再現の手順を付けて送ってあり、0.14.1 以降の課題として cumo 側のトラッカーに記録されている。

## 性能で負けた条件と原因

### 1. 一時配列が Ruby の GC を待つ（A、B、C、E、F）

大きい配列の条件で Cumo が CuPy に負けるのは、ほとんどがこれ。

- cumo は GPU のメモリの確保と解放を `rb_gc_adjust_memory_usage` で Ruby に知らせる（`ext/cumo/narray/narray.c` など）。一時配列は GC が回るまでメモリプールに戻らない（cumo #221、#222）。
- そのため、数 MB 以上の一時配列を作るステップでは minor GC が頻繁に走る。malloc の上限（既定で 16 MB）を 1 本で超える配列では、作るたびに走ると見ている。
- 1 ステップのうち GC が占める時間（`GC.stat`、単発、0.14.0）:

| 題材と条件 | 1 ステップ | GC | CuPy |
|---|---|---|---|
| B、2048²、fp32 | 12.8 ms | 12.0 ms | 6.29 ms |
| B、4096²、fp32 | 44.3 ms | 42.7 ms | 38.9 ms |
| F、64 × 10000 本、fp32 | 0.086 ms | 0.057 ms | 0.058 ms |
| C、`rfftn` 512³、fp32 | 20.2 ms | 2.6 ms | 18.6 ms |
| A、30000 フレーム、fp32 | 2.77 ms | 2.62 ms | 1.50 ms |

- 0.14.1 では、混ぜた演算の一時配列が減った分だけ、GC も減った（B の 2048² で、同じ日の同じ数え方で 13.1 → 11.0 ms。3 番）。GC を待つ仕組みそのものは変わっていない。
- 配列が L2 キャッシュに収まる大きさ（E の 1024²〜2048²）では、GC を待つ間に毎ステップ新しいメモリを使うので、同じカーネルでも遅くなる（E の cuFFT のカーネルで 117 µs と 98 µs）。
- **効いた対策:** ステップの一時配列を使い終えた時点で `NArray#free` すると、F の 64 × 10000 本は 0.085 → 0.059 ms（CuPy は 0.058 ms）、E の 2048² は 2.30 → 1.79 ms（CuPy は 1.59 ms）になった。`Cumo::FFT` の中の一時配列（軸を移すコピー、詰め物、スペクトル）は解放していないので、そこも返せばもっと縮む見込み。
- **棄却した対策:** `RUBY_GC_MALLOC_LIMIT` などを上げると、B の 2048² は 12.7 → 7.07 ms になるが、プールが 495 MB から 2.4 GB に増える。F では、かえって遅くなった（0.086 → 0.112 ms）。申告の仕組みは、GC が GPU のメモリを知らずにプールが際限なく増えるのを防ぐためのものなので、上限を上げるのは解決にならない（cumo 側のセッションの指摘）。
- cumo 側の案（0.14.1 以降）: 申告を「プールが実際に cudaMalloc で増えたときだけ」にする。`Cumo::FFT` の一時配列をその場で返す。

### 2. 最初の呼び出しが遅い（全題材の初回）

- プロセスの最初の呼び出しは、Cumo が CuPy の 1.6〜14 倍遅い。D で切り分けると、cuFFT のプランの生成（Cumo と CuPy で同じくらい）ではなかった。cumo の要素ごとの演算のカーネルを、型と演算の族ごとに CUDA が遅延して読み込む手間で、1 族あたり 3〜30 ms かかる（cumo #583、#590、#610）。
- `CUDA_MODULE_LOADING=EAGER` にすると、初回は CuPy に近づく（D の `fftconvolve` で 36.2 → 7.0 ms、CuPy は 4.3 ms）が、最初の CUDA の呼び出しが 28 ms から 1.18 s に延びる。
- cumo 側で、リリース後の性能の課題として記録されている。
- cumo 0.15.0 で、縮約を使う題材の初回が縮んだ。#634 で `sum`、`mean`、`max`、`min` とベクトルの `dot` が別のモジュールになった効果と見ている。0.14.1 と同じラウンドで交互に測ると、G の Welch が 68.0 → 43.1 ms、A が 128 → 102 ms、E の `fft2` が 54.9 → 47.9 ms だった。要素ごとの演算のカーネルの読み込みは変わらず、B、C、D、F の初回は変わらなかった（[results/cumo-0.15.0.md](results/cumo-0.15.0.md)）。

### 3. 複素数と実数を混ぜた演算の型の変換（E、B、C）: 0.14.1 で直った

- 0.14.0 では、同じ精度の複素数と実数の + − × ÷ が、どちらの順序でも、実数の側を複素数に変換するカーネルを 1 本足していた（E の 1024² で 1 本約 20 µs）。変換した一時配列も 1 本増える。CuPy は、型を混ぜたカーネル 1 本で済ませる。このページは当初「割り算だけが変換し、掛け算は変換しない」と書いていたが、誤りだった（cumo 側も 2026-10-20 に訂正した）。
- **cumo 0.14.1（#632）で、変換せずにカーネル 1 本で計算するようになった。** 同じラウンドの交互の計測で、0.14.0 より E が 1.03〜1.07 倍、B が 1.10〜1.18 倍、C が 1.10〜1.12 倍速くなった。E の 1024² と、fp32 の 2048² の `fft2` は変わらなかった（[results/cumo-0.14.1.md](results/cumo-0.14.1.md)）。
- 残り（どちらも cumo 側のトラッカーにある）: Ruby の Complex のスカラー、精度の違う組、整数と複素数は、0.14.1 でもまだ変換する（cumo 側のセッション）。#632 で足したカーネルは汎用の反復子の版しか無く、連続した配列でも `_dim1` を通る。E の 1024² で、`div_r` は複素数どうしの `div_vec` より 4.7 µs 遅かった。これがその差の原因かは、まだ確かめていない（疑い）。

### 4. `real` と `imag` がコピーを作る（E、G）

- Numo に合わせた仕様（CuPy はビューを返す）。E の `fft2` の経路で 1 本、G の Welch の絶対値の 2 乗で 4 本ずつ、カーネルが多い。直すものではないが、差の内訳として書いておく。

## 計画の候補のうち、棄却したもの

計画の第十一段階は、候補として 4 つを挙げていた。測った結果、どれも主な原因ではなかった。

| 候補 | 結果 |
|---|---|
| 末尾でない軸の advanced layout（C） | **入れると遅くなる側。** CuPy は advanced layout（ストライドのまま）で変換し、512³ の 2 軸の変換で Cumo の 6.5 倍遅かった。Cumo の「転置してから連続した配列を変換する」作りのほうが速い。cumo 側も、advanced layout は入れない方向に計画を改めた |
| `fftshift` のコピーの削減（E） | Cumo も CuPy も 4 ブロックのコピーで、時間もほぼ同じ（1024² で 7.9 µs と 9.4 µs）。差の原因ではない |
| 正規化のコピーへの畳み込み（B） | 正規化の割り算は両者とも別のカーネルで、時間も同じくらい（F で 22 µs と 18 µs）。B で負けた主な原因は GC |
| LRU の破棄の手間（G） | キャッシュを溢れさせる条件で、Cumo が 1.55 倍速かった。プランを捨てる前の `cudaEventSynchronize`（1 ステップに 20 回）は、差を逆転させるほど効いていない |

## cumo 以外で見つけたもの

- **numo-pocketfft 0.7.0:** `fftn` と `rfftn` に 0 次元の配列を渡すと、C の拡張が `NA_SHAPE(x)[n_dims - 1]` を `n_dims = 0` のまま読み、配列の外を読む。プロセスの状態によって `NoMemoryError`、値を返す、返らない（TERM でも止まらない）のどれかになる（[results/pocketfft-compat.md](results/pocketfft-compat.md)）。numo-pocketfft には報告しない（2026-10-18、ユーザーの判断）。
- **narray-llm の Whisper の log-mel:** fp32 の DFT の表（角度 k·n·2π/400 を fp32 でそのまま作る）は、fp64 の正しい値から 1.02e-3 ずれる。rfft にすると 9.5e-8 になる（[results/whisper_mel.md](results/whisper_mel.md)）。narray-llm は、角度を k·n mod 400 に畳む直しを取り込み（narray-llm `2faa1db`）、rfft への置き換えは見送った。
